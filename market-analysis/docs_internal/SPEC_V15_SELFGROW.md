## §0 诚实红线（5 命门逐条作答）

### 命门 1：候选空间如何有界
v1.5 **不**开放"机器自主发明新命名效应"的无界元空间（那正是被 NO-GO 的 P-E 路径）。有界性来自一条新规则：
- 自动候选生成**只允许以"维度扫描"形式发生**：在一个**已经预注册、已经双审通过**的候选族（如日历族、连跌族）内，人工提议并双审一个**新的结构维度**（如"逐月""逐十分位""逐 lookback 窗口"），双审对象是"这个维度该不该测"，**不是**"测出来哪个格点该留"。
- 一旦维度获批，格点由 `itertools.product` 式机械展开生成**该维度下的全部格点**，零筛选、零人工挑选个体候选。
- 每次维度扫描仍然写死 `N_DECLARED` 增量（沿用 `candidate_space.py` 现有模式：每次扩声明都是一段带日期的注释块 + 常量加法），继续 test 对账（`test_candidate_space.py` 断言 `len(enumerate_candidates())==N_DECLARED`），继续代码评审锁定。
- 硬顶：见 §6 判断点 4（建议每季度新增候选数设软预算，防止"每次都合规但累计仍让分母失控膨胀"）。

### 命门 2：FDR 诚实性
无需新代码：维度扫描生成的候选照样落进 `candidate_space.enumerate_candidates()` 返回的同一个列表，`quality_gate.adjudicate(expect_n=N_DECLARED)`（`quality_gate.py:23-26`）已经断言 `len(results)==expect_n`，分母不完整直接抛异常——这道门本来就通吃"人手加的候选"和"维度扫描加的候选"，不需要区分来源。跨族 BY-FDR（`quality_gate.py:31`）、族内 BY（`:34-41`）都是对全体候选统一池化，机械扫描出来的候选自动被平等计入，无特殊待遇也无法被悄悄排除。

### 命门 3：OOS 锚点纪律
同样无需新代码：`candidate_registry.sync()`（`candidate_registry.py:41-57`）已经会对"当前候选空间里、登记簿里还没有的 candidate_id"逐条 append 一行 `declared_date=today`，且这个写入受 `verify_output.py` 4c 门（`verify_output.py:617-642`）保护——相对 git HEAD 只能 append，改历史行/倒填直接拒绝发布。维度扫描新增的候选走的是同一条路：`sync()` 一跑，全部新格点在**同一天**拿到同一批锚点。§4 会加一条新测试，专门断言"同一次维度扫描的全部格点必须共享同一个 `declared_date`"（见下）。

### 命门 4：防 p-hack（本规格新增的部分，因为这是 P-E 栽的坑）
这是 §0 里唯一需要**新护栏**（而不是复用现成机制）的一条，因为 P-E 恰恰死在这里：
1. **维度理由必须独立于本仓库已见结果**：新增维度的双审提案必须写明"为什么现在测这个维度"，理由来源只能是 (a) 该维度本身**结构完备、自带穷尽性**（如"星期""月份""既有十分位分箱标准"——这类维度的"该不该测"不依赖任何候选表现好坏，是范畴本身的自然延伸），或 (b) 独立于本项目已见 p 值/verdict 的外部先验/文献引用（同 `candidate_space.py` 现有 8 次扩声明的写法）。**禁止**"因为某候选/某因子最近表现出彩，所以把它所在的维度展开测更细"这类理由——这正是 P-E BLOCKER-1 的翻版，必须在双审时逐句核对提案文字有没有隐含"已经看过这个维度局部效果不错"。
2. **原子整族提交**：一次维度扫描必须在同一次 spec 变更（同一次 `candidate_space.py` 改动 + 同一次 `sync()`）里放出该维度的**全部**格点，禁止先加几个观察反应、几天后再"顺手"补齐剩下的——那是分批筛选的变种。§4 加 CI 守卫检测这个模式。
3. **仍然禁止连续参数扫描**：只允许对**离散、预声明、有限**的维度做全展开（月份12个/十分位10个/既有hold窗口集合），不允许"阈值从0到100逐1扫一遍"这类连续网格——这条红线从 v1.0 起就没变过，本规格不动它。

### 命门 5：与现有门的接口
`autodiscovery.py` / `quality_gate.py` / `oos_gate.py` / `knowledge_base.py` / `flicker.py` **全部不用改一行**——它们的设计本来就是"喂什么候选都能吃"的通用引擎（这是这套架构过去三轮候选扩容都没动它们的原因）。唯一新增的是一个**开发时辅助工具**（§1/§2 展开），帮人把"维度扫描"这个动作做得更规范、更难出错，本身不进 `run_all.py` 生产流水线。

## §1 自动提案机制设计：维度扫描自动化（Dimension-Sweep Automation）

**这是什么**：把 `_CAL_MONTHSWEEP` 已经验证过的安全模式（机器机械展开一个已获批的结构维度，人不挑格点）形式化、工具化，作为 v1.5 的候选自动生成方式。

**这不是什么**：不是"机器读数据后自己想出新命题去测"（P-E/HARKing 路径，已 NO-GO）；不是每日 run_all 里自动决定"今天要不要加新维度"（那是把判断下沉给机器，正是 `SELF_GROWING_PLAN.md` §2 开篇"中心危险"描述的东西）。维度扫描永远由人**在写规格阶段**发起，是一次性的 spec 变更，不是流水线的日常步骤。

### 1.1 提案生成算法（工具支持，纯组合，不碰任何市场数据）
新增 `market-analysis/scripts/dimension_sweep.py`（开发时 CLI 工具，不进 `run_all.py`）：
1. 输入：一份声明式描述（family、dimension_name、values 列表、`prior_statement`、`prior_cite_or_completeness_argument`、结构完备性自检——"这个维度的全部取值是否已经穷尽列出，有没有隐藏的连续参数"）。
2. 校验：`prior_statement` 非空、`values` 是有限离散集合（拒绝任何看起来像连续扫描的输入，如等差数列长度>某阈值且步长像"扫描"）。
3. 输出：
   - `candidate_space.py` 对应 family 函数的建议 diff（追加维度、机械 `for` 展开全部 values，不做条件筛选）。
   - `N_DECLARED` 增量计算 + 断言脚手架（同现有 test 模式）。
   - commit message 模板（含维度理由，供 review 时逐句核对"理由是否独立于已见结果"）。
   - **不**自动跑 `candidate_registry.sync()`——那一步仍在人工 review 通过、代码合入后由 `run_all.py`/开发者手动触发，与现有流程一致，不新增自动化面。
4. 该工具本身**不 import 任何统计/数据模块**，纯字符串/列表操作，同 P-E 规格 §12.5 对"零统计"的护栏要求（沿用同一条纪律，即便 P-E 整体已 NO-GO，那条具体护栏设计是对的）。

### 1.2 安全性质三条（对应命门4的三条护栏）
① 维度审查在先且理由独立于已见结果 ② 原子整族提交 ③ 候选级别零人工挑选。三条同时成立，才不重蹈 P-E 覆辙——**任一条被绕过，这个机制就退化回 P-E**，建造和审查时都要把这三条当作不可谈判的门。

### 1.3 与"维度审查"仍然是人的这一事实的关系
命门里"防p-hack"最难的部分——证明维度选择独立于已见数据——机器测不出来，只能靠双审时人工逐句核对。这条防线的边界必须写进 §6 让用户知情：**这套机制自动化的是"打字/展开/记账"，不是"想出该测什么"；"该测什么维度"仍然是且必须是人的判断，双审仍然是这里唯一的真实防线。**

## §3 v1.5 范围内 / 外

**范围内**：
- 维度扫描机制形式化，写入 `candidate_space.py` 顶部注释作为标准扩展方法（`_CAL_MONTHSWEEP` 的模式从"一个特例"变成"官方推荐路径"）。
- `dimension_sweep.py` 工具（机械生成 diff 建议 + N_DECLARED 计算 + commit 模板）。
- CI 守卫：原子性检测（同族格点锚点不一致 → 报警）+ 维度理由字段非空校验。
- 至少 1 个真实维度扫描作为首发案例落地（哪个维度由 §6 判断点2 拍板）。

**范围外（明确不做，理由）**：
- **P-E 式"机器提议全新命名效应待人审"**——已 NO-GO，不重开，除非用户明确要重议且能提供打破 BLOCKER-1（元空间独立于 peek 不可证伪）的新证据（如真正干净的外部冻结来源，见 §6 判断点5）。
- **任意连续参数/阈值自由扫描**——老红线，本规格不动它，`dimension_sweep.py` 主动拒绝这类输入。
- **完全无人工的"机器自主决定测什么 + 自动进分母"闭环**——`HANDOVER.md` line 198 字面意义上的"全自动"不在本版范围。我不认为这是安全的，也不会在缺少你明确书面拍板、且没有解决 BLOCKER-1/2 的前提下把它写成可执行规格（见 §6 判断点1）。
- **深度学习 / 新数据源用于候选生成**——不相关，本次未提及，不纳入。
- **每日 run_all 内的"今天要不要加新维度"式判断**——维度扫描永远是一次性的、人工触发的 spec 变更，不进日常流水线。

## §4 验证方案（上线前证明它没作弊 FDR）

1. **纯噪声维度扫描注入**：合成一个新维度，全部格点用随机数生成的合成收益序列（无真实信号），跑通"声明→展开→进分母→BY-FDR 裁决"全链路，断言几乎全部落 `dead`/`inconclusive`（≈期望假阳率），且候选没有被悄悄排除出分母（`m_total` 增量与新增候选数精确相符）。沿用 `PLAN_V15_AUTODISCOVERY.md` §6 已有的"纯噪声家族→校正后入选≈期望假阳率"验证范式，本次专门覆盖"维度扫描"这一新增来源。
2. **合成 look-ahead / 分批筛选检测**：伪造一次"非原子提交"——同一维度先落地 3 个格点、模拟等待观察后再补齐剩下的格点（不同批次的 `declared_date` 不同）。断言新增 CI 守卫能抓到并阻断发布（"迟到格点"锚点晚于同族其余格点、缺少同批注册记录 → fail）。
3. **原子性单测**：扩展 `test_candidate_registry.py` / `test_registry_guard.py`，加断言"任一 family 内、标记为同一次维度扫描的全部候选，其 `declared_date` 必须相同"。
4. **维度理由可审计性测试**：新增维度声明块（同现有 8 次扩声明的写法）必须含 `prior_statement`/`prior_cite`（或结构完备性论证）字段，CI 断言非空。**明确边界**：这只管得住"有没有写理由"，管不住"理由是不是真的独立于本仓库已见结果"——那条防线是人工双审的责任，不是机器能测出来的，§0 命门4已写明，这里重申以防审查时误以为这项测试能替代双审。
5. **注入已知无效候选的对称检验**：同时注入一个已知有效的合成信号（真信号+噪声混入同一维度扫描），断言 BY-FDR 正确识别出真信号存活、噪声组正确判死——防止守卫本身矫枉过正把所有新维度都判死。
6. **回归门**：整条 run_all 链路指纹（既有候选 p/recent_p/verdict）在加入新维度扫描前后**逐字节不变**（沿用 T1/#5 等历史改动的验收标准），证明新机制不干扰既有候选的裁决。
